## What worked

- The pre-sprint model conversion pattern (established in sprint 19 with CodeFormer) held up:
  converting and committing both CoreML models to a dedicated branch before spawning any impl
  session avoided any mid-implementation surprises about model I/O shapes.
- Merging the pre-sprint model PR (#194) into `main` *before* spawning impl sessions — rather
  than letting impl branches fork off the sprint branch and merge to main first (the sprint 19
  pattern) — worked cleanly and is simpler to reason about. Recommend making this the standard
  going forward (see skill proposal below).
- Two-round repair loops caught real, distinct issues on both PRs (not false positives):
  - #164: impl bumped SwiftLint's `file_length`/`type_body_length` thresholds instead of
    extracting to a new file, exactly as the sprint plan had anticipated and warned against.
    Caught by manual orchestrator inspection (not the automated review pass), fixed by
    extracting `SlideshowView+AIEdits.swift` as planned.
  - #165: automated review caught a real concurrency bug — two pre-existing AI-edit functions
    were missing a `!isColorizing` guard, allowing a race if triggered while colorization was
    in flight.
- Resuming a quota-interrupted session (via `mcx claude send`) rather than discarding its
  work was the right call: the session had left substantial, buildable, uncommitted progress
  and only needed to finish one piece (grayscale-detection alert) plus commit/push/PR.

## What didn't

- The automated review pass for #164 missed the SwiftLint-threshold-bump issue entirely —
  it only caught the missing test-acknowledgement sentence. The threshold-bump issue was only
  caught because the orchestrator cross-checked the PR diff against the sprint plan's explicit
  pre-sprint warning. The review prompt doesn't currently instruct the reviewer to check PR
  diffs against sprint-plan warnings.
- `mcx phase run review/repair` failed twice with "phases only run from branch main" because
  impl/repair sessions leave the main checkout on the feature branch when they finish. This is
  documented behavior (run.md's "Important ordering" note) but still costs a retry each time.
- One impl session (#165) hit the usage quota mid-task. Zero indication in advance; only
  visible after the session.result event fired with the quota message.
- Daemon had 7 stale `impl`-phase work items left over from sprints 17–19 (never untracked
  after their PRs merged) sitting in `mcx tracked` output. Harmless but noisy — cleaned up
  during this sprint's run phase.

## Patterns established

- **Merge pre-sprint model PRs to main before spawning impl sessions**, not after. Simpler
  branch topology than the sprint-19 pattern (impl branches forking off the sprint branch).
- **Cross-check PR diffs against the sprint plan's own stated risks** (e.g. an explicit
  "watch out for X" note in the plan) as a manual orchestrator step, not just delegate this to
  the automated review prompt — the review prompt's checklist doesn't include "does this diff
  contradict something the sprint plan explicitly said to do."

## Skill proposals

- **Applied:** added a `run.md` rule that any diff touching `.swiftlint.yml`'s
  `file_length`/`type_body_length` values is a repair-worthy review finding (extract instead
  of raising the threshold). See "What didn't" above.
- **Proposed, not applied:** `.claude/phases/review.ts`'s review prompt template doesn't ask
  the reviewer to cross-check the PR diff against the sprint plan's own stated risks/warnings
  (e.g. sprint-20.md explicitly predicted the file-length breach and named the fix). The
  automated review missed this; only manual orchestrator inspection caught it. Adding
  "read the sprint plan file and check the diff doesn't contradict anything it explicitly
  flagged" to the review prompt would close this gap, but `review.ts` is executable
  automation code (runs with full shell/mcp access) rather than prose — leaving this for Joe
  to review and apply rather than editing it unilaterally.
