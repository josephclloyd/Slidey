- **A spawned session's own `gh pr create` command failed on a bash heredoc quoting bug**

  divergent-branches prompt, rather than fast-forwarding `main` cleanly. Recovery was a
  plain `git checkout main` since the fetch had already updated the local ref — no damage,
  but avoidable.
- **Two review sessions gave clearly approving comments without emitting the literal
  `VERDICT: clean` token** the prompt requested. Treated as clean based on content, but this
  is a prompt-following gap worth tightening if it recurs.
- **5h quota lag lasted ~12+ hours** in one instance (previously documented as 10-15

## Patterns established
- Flagging a known risk (stale suggestion in the issue text, or an interaction hazard with
  existing code) directly in a follow-up message right after spawning — before the session
  has gone deep into a wrong assumption — is now proven twice in one sprint. Worth writing
  into `run.md` as a standing practice: if the sprint plan's own notes flag a specific risk
  for an issue, pass that risk to the impl session explicitly rather than trusting it'll
  read the plan file.
- Quota-hit resume nudges should always name the exact file/symbol left incomplete (not just
  "continue") — every successful resume this sprint did this, and it avoided the resumed
  session re-deriving context it already had.

## Proposed skill improvements

1. **`run.md`: flag known plan-time risks to the impl session explicitly, right after
   spawn.** This sprint's plan file called out #169's stale key-binding suggestion and
   #136's gesture-interaction risk in its per-issue notes — both were passed to the impl
   session via a `mcx claude send` follow-up immediately after spawning, and both issues
   landed with 0 repair rounds. Worth codifying as a standing step: "if the sprint plan's
   notes flag a specific risk for an issue, send it to the impl session as a follow-up
   right after spawn — don't rely on the session reading the plan file itself."

2. **Prefer `--body-file` over inline heredocs for `gh issue create`/`gh pr create` bodies.**
   Hit a bash heredoc quoting failure twice this sprint from two different actors — once by
   the orchestrator itself (filing GitHub issues with apostrophes in the body text) and once
   by a spawned impl session (#216's own `gh pr create`, `bad substitution: no closing ')'`).
   Both recovered fine, but this is a repeatable, avoidable failure mode. Proposal: write the
   body to a temp file first (`Write` tool for the orchestrator; a plain file write for
   spawned sessions) and pass `--body-file <path>`, rather than `--body "$(cat <<'EOF' ...)"`.

3. **Use `git fetch origin main && git merge --ff-only` instead of bare `git pull` in the
   main checkout.** A bare `git pull` hit a divergent-branches prompt this sprint and left
   HEAD detached at `FETCH_HEAD`. Local `main` had already fast-forwarded via the fetch, so
   recovery was trivial, but a bare `pull` in a checkout that spawned sessions actively
   branch from is a needless hazard — `merge --ff-only` fails loudly instead of prompting
   for a reconciliation strategy.

4. **Tighten the review spawn prompt's verdict instruction, or accept content-based
   verdicts explicitly.** Two review sessions this sprint gave unambiguous LGTM comments
   without emitting the literal `VERDICT: clean` string the prompt requested. Handled by
   reading the comment content instead of the literal token, but if any future automation
   parses strictly on that token, it would stall. Either strengthen the prompt's phrasing
   (e.g., "your final message must consist of exactly this line and nothing else") or
   document that content-based fallback is acceptable when the token is missing but the
   comment is unambiguous.
