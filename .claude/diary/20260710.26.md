## What worked
- **Honest scoping over overclaiming.** #240's own issue notes flagged real uncertainty
  about whether the bundled SwinIR model (trained for JPEG artifacts) would generalize to
  general sensor noise. The impl session tested this, found it doesn't clearly outperform
  the classical filter on true sensor noise, and documented that honestly in the PR rather
  than shipping a "smarter denoiser" that wasn't actually smarter. This is exactly the
  outcome the plan-time risk-flagging was meant to produce.
- **Flagging risks at spawn time** (Sprint 24/25 pattern) worked again: #240's impl was told
  upfront to verify SwinIR's generalization before committing to reuse, and to ship as a
  separate toggle rather than replacing the classical HUD. Both landed as instructed.
- **Trying a quota-hit resume immediately, rather than waiting out the full displayed
  window,** succeeded — see below, this is now upgraded to a confirmed pattern rather than
  a hopeful guess.

## What didn't
- **A review caught a claimed-but-not-actually-done refactor.** #240's PR description said
  a `runSwinIRInference()` helper was "extracted" from artifact removal, but the diff showed
  artifact removal still had its own ~160-line inline copy — the extraction was only wired
  up for the *new* AI Denoise path. Worth noting: this is a PR-description-vs-diff mismatch,
  not a functional bug — the feature worked, the description overstated the cleanup. Review
  caught it because it checks the diff against the stated claims, not just "does it work."
- **Missing tests for a new `Codable` enum case** — same class of gap as noted in CLAUDE.md's
  explicit testability requirements, caught in the same repair round as the above.
- **Confusion over Anthropic account quota mechanics mid-sprint.** Joe noticed `mcx status`'s
  `Extra` usage line jump from `$0` to `$336` and asked whether more usage should be
  available. Investigation found `hasExtraUsageEnabled: true` in the local Claude Code
  config — extra usage was already on, not something to toggle. The practical resolution
  came from just trying: a resume attempt succeeded well before the 5h window's *displayed*
  reset time, even while `mcx status` still showed 100% used. This confirms (again, more
  clearly than prior sprints) that the displayed quota/reset numbers can lag real
  server-side state significantly — the fix isn't to wait out the display, it's to just
  attempt the resume and let it fail if it's still genuinely blocked.

## Patterns established
- **Just attempt a quota-hit resume rather than waiting for the displayed reset time.** It
  costs nothing if it fails (the session just reports the same error again), and it
  succeeded well before the displayed reset in this sprint. Previous sprints' guidance to
  "wait ~10-15 minutes and recheck" undersold how large this lag can actually be — attempt
  first, wait only if the attempt itself fails.
- **Memory audit found and fixed real staleness this cycle** (not just confirmed
  load-bearing status): `project-sprint17-patterns.md`'s key-binding registry and
  compositing-pipeline-order sections had drifted from CLAUDE.md twice now. Rewrote both
  sections to explicitly defer to CLAUDE.md as the single source of truth instead of
  attempting to keep a second copy current — and corrected a third section (per-image
  persistence) that was flatly wrong since Sprint 23 reverted the feature it described.
