## What worked
- **The `review_round_retry` fix from Sprint 27's retro validated itself immediately.**
  #259 hit two genuine quota-exhaustion review-spawn failures (0 tokens each) as the
  five-hour window ran out. Both times, setting the retry flag before re-running the phase
  kept `review_round` at 1 instead of advancing toward the cap — confirmed directly via
  `phase_state_get`. This is exactly the scenario the fix was built for, and it worked on
  the first real test.
- **Bundle detection handled cleanly.** #261 and #262 were spawned in parallel from the
  same base and independently made the identical Local Adjustments fix. Rather than
  treating review's "undisclosed behavioral change" finding as a real defect needing a
  from-scratch fix, recognizing it as a duplicate-merge artifact and sending the repair
  session that specific context turned a potentially confusing repair loop into a
  one-command `git merge origin/main` resolution.
- Verifying a mid-run test failure against clean `main` before filing an issue (rather
  than assuming a regression or blocking the PR) correctly identified
  `testLoopDisabledStopsAtLastImage` as pre-existing flakiness unrelated to the diff in
  flight.

## What didn't
- **Quota management needed three separate judgment calls this sprint**, more than any
  prior sprint: an 85% monthly extra-usage warning before starting any impl sessions, a
  93% five-hour-window warning before starting #259, and then two real spawn failures
  before the actual wait. Surfacing each to Joe rather than silently proceeding or
  silently stopping was the right call, but it's a sign the sprint's total workload
  (6 issues across two back-to-back sprints, on top of the interactive post-#219 bug
  fixes) is pushing close to whatever monthly ceiling is set. Worth watching whether this
  becomes a recurring pattern.
- **The daemon was unstable at the very start of the run phase** — `mcx monitor` failed
  twice with a connection error right after a fresh restart, before stabilizing. Cost a
  few minutes of diagnosis but no real damage; the fix (wait for `mcx status` to show a
  stable, climbing uptime with all 8 servers `connected` before spawning anything) is now
  documented in this sprint's Results/Deviations, worth watching for recurrence.

## Patterns established
- **Quota-exhausted review retries: verify the retry flag actually held.** After setting
  `review_round_retry` and re-running `mcx phase run review`, confirm via
  `phase_state_get` that the round counter didn't advance, rather than just trusting the
  spawn action came back. Cheap to check, and catches a silent regression in the fix
  itself immediately rather than discovering it three rounds later.
- **Bundle-detection repair sessions need explicit context, not just the raw review
  comment.** The reviewer correctly flagged the duplicate change as suspicious but had no
  way to know a sibling issue had already landed the identical fix — that context only
  exists in the orchestrator's cross-issue view. Send it explicitly via `mcx claude send`
  rather than expecting the repair session to piece it together from `gh` history.
- **Daemon health check before spawning: don't trust a single `mcx status` reading right
  after a restart.** Uptime near 0s with any server still `connecting` means wait and
  recheck, not proceed — this cost real time this sprint when skipped implicitly the
  first time.
