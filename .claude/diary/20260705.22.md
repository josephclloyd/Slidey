## What worked

- **First sprint sized above 2 issues (4), fully serialized.** Worked cleanly — no
  cross-branch merge conflicts, since every issue branched from a clean main after the
  previous one merged. Confirms the "scale after clean sprints" guidance was reasonable to
  act on.
- **Proactively warning a later issue's impl session about a pattern the same sprint had
  already hit.** After #129's repair rounds flagged toast-message conventions (2.5s delay,
  `error.localizedDescription`), #139's spawn message included that exact guidance up front
  — and #139's session didn't add any toast at all, so it wasn't tested, but the broader
  pattern (proactively transferring same-sprint lessons forward) is worth keeping.
- **Reconciling a repeated review finding across issues instead of re-litigating it.** #139's
  review flagged the same "menu item not really disabled" issue #129's review had already
  accepted as intentional precedent. Rather than let #139's repair session improvise a
  different (inconsistent) answer, the orchestrator gave explicit instructions to reference
  the #129/#204 precedent and decline the one-off `@FocusedValue` fix — then filed #206 to
  do it properly, once, across the whole File menu. Consistency preserved, no wasted
  architecture work, and the underlying want (real disabled state) wasn't lost, just deferred
  to the right scope.
- **Overriding a false-positive `needs-attention` transition.** #129 hit the phase graph's
  max-review-round cap (2) purely because review found two *separate*, *minor*, *already-fixed*
  nits across two rounds — not because anything was actually broken or unstable. The
  orchestrator independently re-read the full diff and comment thread, confirmed both fixes
  were correct and no threads were open, and manually transitioned to `done` with an explicit
  `forceReason` rather than parking a demonstrably-finished PR for Joe to re-verify. Judgment
  call, not a shortcut — the same verification a human orchestrator would have done before
  accepting the override.
- **Diagnosing a CI-only failure by reading the actual code, not just pattern-matching the
  error message.** #100's type-checker timeout moved to a different line after each of two
  extraction attempts. Rather than keep telling the impl session "extract more" blindly, the
  orchestrator read `coreView`'s modifier chain directly, found the real bottleneck (~15
  pre-existing `.onChange` handlers, not the feature's own code), and gave a specific,
  correct splitting strategy (`coreViewBase` + `coreView`) that fixed it on the first try
  once given that diagnosis.
- **Doing purely mechanical recovery work myself instead of waiting on quota.** When a quota
  hit left an already-written, already-build-verified fix uncommitted, the orchestrator
  committed and pushed it directly rather than waiting hours for the quota window to reset
  just to run `git commit`/`git push`. This is consistent with "never implement directly" —
  no code was written or decided, only already-authored, already-verified work was persisted.

## What didn't

- **The `/implement` sprint-plan-check fix from Sprint 21's retro doesn't actually work.**
  It greps local `.claude/sprints/sprint-*.md` files, but the *current* sprint's plan lives
  only on the unmerged `sprint-N` branch until retro time — so for all four issues this
  sprint, the automated check found nothing (or, in #129's case, false-matched unrelated
  older sprint files containing the same issue number as incidental text). Every single impl
  session needed a manual `mcx claude send` redirect with the actual plan content. This is a
  real, fully reproducible bug, not a one-off — see skill proposal below.
- **`repair.ts` doesn't clear its own `repair_session_id` between rounds.** When review sent
  a PR back for a second repair round, `mcx phase run repair` returned `in-flight` pointing
  at the first round's (already-finished) session instead of spawning a new one. Had to
  manually delete the stale state key each time this happened. Same root shape as the
  `/implement` bug: state that should be reset on a phase re-entry isn't.
- **Orchestrator error: `git add -A` swept in an untracked `.mcx/` daemon-log directory**
  during a manual commit of quota-interrupted work. Caught immediately (before opening a PR)
  and fixed with a follow-up commit plus a `.gitignore` entry, so it can't recur — but it's a
  reminder that even "purely mechanical" git operations deserve the same specific-filename
  discipline as everything else in this project's stated git hygiene.
- **The `SlideshowView` type-checker timeout took three rounds to actually fix**, and the
  first two rounds were plausible-but-wrong diagnoses (assumed `overlayViews`, which *was* a
  real problem but not the *only* one). `coreView`'s modifier chain was already close to the
  type-checker's limit before this sprint even started — the four small, individually
  reasonable features this sprint (especially #100's one new `.onChange`) collectively tipped
  it over. This is a structural debt that will recur on the next feature that touches
  `coreView`, regardless of how small that feature is.

## Patterns established / reinforced

- Scaling sprint size from 2 to 4 issues, fully serialized, is viable when the codebase and
  pipeline have proven stable across several prior sprints — worth continuing to scale
  further if this holds.
- When two different issues in the same sprint hit the *same* review finding, resolve it
  once (via precedent + a follow-up issue) rather than re-deciding it per-PR.
- A `needs-attention` transition should be treated as a strong *default*, but is override-able
  by the orchestrator when independent verification shows it was a round-cap artifact, not a
  real blocker — document the override explicitly (`forceReason`) either way.
- `coreView`'s modifier chain is now understood to be near-permanently close to the
  type-checker's tolerance, independent of any single feature's complexity — see skill
  proposal below for baking this into pre-sprint risk assessment.
