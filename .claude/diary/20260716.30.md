## What worked
- **Being wrong about the root cause (twice, on the same feature) still produced good
  outcomes because the wrongness was caught and corrected quickly each time.** The
  original #274 diagnosis (add `inputEyes`) was wrong — the impl session caught it and
  pivoted to a better fix. That fix's threshold was ALSO wrong — Joe caught it within
  minutes via live testing, and it got root-caused and fixed same-session. Neither miss
  was catastrophic because the feedback loop (impl session double-checking assumptions;
  Joe actually using the feature) closed fast each time.
- **The daemon protocol-mismatch incident was handled correctly under uncertainty** — surfaced
  the risk clearly (22 sessions "orphaned," confirmed they were all stale), got explicit
  sign-off before the destructive-sounding action, and the actual outcome was exactly as
  predicted (no real work lost, direct fix for the resulting `.mcx.lock` drift).

## What didn't
- **Red-eye detection is now 0-for-2 on actually being verified working.** Both #278 and
  #279 were shipped/proposed based on code reasoning and visual inspection of a screenshot,
  not empirical pixel sampling or a running app test — because neither is available in
  this environment. This is a real, recurring gap for any feature whose correctness
  depends on tuning numeric thresholds against real-world image data. Static review
  (even a careful one) cannot catch "this threshold is wrong for real photos" — only
  actually running the feature can, and that's Joe's manual-test step, not something the
  orchestrator or review pipeline can shortcut.
- **The review that approved #278 (VERDICT: clean) reasoned that the approach was sound
  without being able to verify the specific threshold value was well-calibrated.** Not a
  process failure exactly — the review criteria don't include "does this numeric
  threshold work on real data," and probably shouldn't (that's what the manual test
  checklist is for) — but worth naming plainly: a "clean" review verdict for a
  threshold-tuning-dependent feature is a weaker signal than for most other kinds of bugs.

## Patterns established
- **For any feature whose correctness hinges on a numeric threshold tuned against
  real-world data (image pixel values, timing, etc.), explicitly flag in the PR body that
  the threshold is unverified/a judgment call**, not just that tests pass — this sets the
  right expectation for the manual test step rather than implying "reviewed and working."
  Did this for #279; worth doing retroactively-in-spirit for any future PR in this
  category.
- **Post-merge live bug fixes stay in the same session, not deferred to a future sprint**
  — third time this pattern has held (Sprint 27's #219/#260, Sprint 30's #274/#279).
  Consistently the right call when Joe is present and reports something broken
  immediately after a merge.
